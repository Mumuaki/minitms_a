# Детальный документ соответствия кода и документации MiniTMS

**Дата составления:** 13 июня 2026
**Объект анализа:** проект MiniTMS (Google Drive → MiniTMS) — папка документации `docs/` (43 документа) против реализованного кода скрапера и backend, доступного в рабочей папке.
**Метод:** покрыты все 43 документа спецификации; статус каждого определён сопоставлением требований с фактическим кодом (`client.py`/`client_fixed.py`, `parser.py`, `mapper.py`, `scraping_router.py`, `settings.py`, `main_scraping.py`, инфраструктурные файлы) и с собственной матрицей соответствия проекта.

## 1. Резюме для руководства

Проект имеет зрелую, детальную спецификацию (clean/hexagonal-архитектура, REST `/api/v1`, доменная модель, порты, очереди RabbitMQ, безопасность JWT/RBAC). Реально же глубоко проработан и хорошо соответствует документации **только модуль скрапинга Trans.eu на уровне UI-процедур** (логин, поиск, фильтрация, выбор грузов). Остальные слои (REST-API по контракту `spec_api.md`, порты/use-cases, очереди, геокодирование, конвертация валют) либо не реализованы, либо реализованы по другому, упрощённому контракту.

**Собственная оценка проекта** (`architecture/06-spec-compliance-matrix.md`): всего 116 идентификаторов требований; 34 покрыты тестами, 20 запланированы, 62 не сопоставлены. Вердикт самого проекта: для реализованных областей — соответствие ДА; для полной базовой спецификации — НЕТ.

**Итоговая шкала статусов в таблицах ниже:**
- ✅ **Соответствует** — код реализует требование документа.
- 🟡 **Частично** — реализовано не полностью либо с упрощениями/отклонениями.
- 🔴 **Расходится** — код реализует иначе, чем требует документ, либо требование не реализовано.
- ⚪ **Не проверяемо** — только документ (спецификация фронтенда/инфраструктуры), реализующий код в рабочей папке отсутствует.

## 10. Ключевые расхождения — сводка для исправления

1. **Контракт API.** Backend отдаёт `/scraping/*` вместо специфицированного `/api/v1` (`/cargos`, `/vehicles`, `/finance`, `/reports`, `/auth`). Фронтенд-спеки рассчитаны на `/api/v1` → текущий backend несовместим с фронтендом по контракту.
2. **Привязка поиска к ТС.** Спецификация требует поиск грузов по `vehicleId`/GPS-позиции (UC-CARGO-01); код ищет по строкам локаций без привязки к ТС.
3. **Валюта и данные DTO.** Нет конвертации PLN→EUR; теряются `published_at` и `company_rating`. DTO требует EUR.
4. **Геокодирование.** Нет Nominatim/OSRM в `mapper.py` → нет lat/lon, расстояний и полилиний для расчёта рентабельности.
5. **Человекоподобность/безопасность.** Фиксированные задержки и `slow_mo=200` вместо случайных 500–1500 мс (`spec_security.md §4.1`, `automation_rules.md`).
6. **Надёжность.** Нет таймаутов/ретраев/идемпотентности/таксономии ошибок из `03-module-map.md`/`04-module-io-boundaries.md`.
7. **Очереди.** Нет RabbitMQ-архитектуры (`spec_messaging.md`); CHECKLIST предполагает Celery/Redis — расхождение между документами.
8. **Прямая навигация.** `search_offers()` делает прямой `page.goto(/exchange/offers)` вопреки рекомендации навигации через меню.

**Внутренние противоречия самой документации:** единицы веса (кг в `spec_entities.md` vs т в `spec_dto.md`); версия PostgreSQL (14+ vs 15+); шина сообщений (RabbitMQ vs Celery/Redis); GPS-провайдер (Wialon/Navixy vs GPS Guard); цветовые пороги (рентабельность в `spec_value_objects.md` vs отклонения план/факт в `spec_reports.md`); пустая спецификация Telegram при заявленном `TELEGRAM_BOT_TOKEN`.

## 11. Общий вывод

- **Скрапер Trans.eu (UI-процедуры): высокое соответствие** документам `spec_trans_eu.md`, `automation_rules.md`, `Поиск_процедура.md` — с локальными отклонениями (фиксированные задержки, прямой `goto`).
- **Слой данных (DTO/mapper): частичное соответствие** — отсутствует конвертация валют, геокодирование и часть полей; есть внутренние противоречия документации по единицам веса.
- **Архитектура (API, порты, очереди, надёжность): существенные расхождения** — реализован упрощённый контракт скрапинга вместо полного `/api/v1` и hexagonal-портов.
- **Backend-сервисы (auth, fleet, finance, reports, GPS, Sheets, SMTP, Telegram) и фронтенд: реализующего кода в рабочей папке нет** — оценка ограничена анализом спецификаций.

Это согласуется с собственной матрицей проекта (`06-spec-compliance-matrix.md`): для реализованных областей — соответствие есть; для полной базовой спецификации — нет.
