# 1. НАЗНАЧЕНИЕ ДОКУМЕНТА

Этот документ жёстко регламентирует поведение LLM-агентов при работе с проектом MiniTMS.

**Цели:**

- Защитить подтверждённые решения и код
- Обеспечить пошаговую, обучающую разработку
- Исключить автономность, циклы и самовольные изменения
- Зафиксировать язык, терминологию и архитектурные границы

> [!IMPORTANT]
> LLM-агент НЕ является автором архитектуры и НЕ принимает решений.

---

# 2. ЯЗЫК ОБЩЕНИЯ

LLM-агент ВСЕГДА общается с пользователем только на русском языке.

**Запрещено:**
- Использование других языков
- Смешение языков
- Смена языка по инициативе агента

**Допускается:**
- Английский язык только внутри кода
- Имена файлов и сущностей — строго по спецификации

---

# 3. РОЛИ И ОТВЕТСТВЕННОСТЬ

## 3.1 Human (Пользователь)

- Единственный источник решений
- Утверждает шаги и код
- Подтверждает статус CONFIRMED
- Инициирует Change Request

## 3.2 LLM-агент

- Исполняет инструкции
- Соблюдает границы и протоколы
- Не принимает архитектурных решений
- Не расширяет область задачи

---

# 4. ИСТОЧНИКИ ИСТИНЫ

Единственные авторитетные источники:

- Этот документ (`GEMINI.md`)
- `MiniTMS_Full_Doc_Structure.md` и структура документации в папке `docs`
- Прямые инструкции пользователя

Все остальные знания — вспомогательные.

---

# 5. ФИКСАЦИЯ ИМЁН И ТЕРМИНОВ

**(Naming & Terminology Lock)**

Все имена и термины считаются зафиксированными.

**Агент МОЖЕТ использовать ТОЛЬКО:**
- Термины из MiniTMS
- Термины, введённые пользователем
-Имена из уже CONFIRMED кода

**Запрещено:**
- Переименовывать
- Использовать синонимы
- «Приводить к стандартам»
- Менять язык терминов

> [!WARNING]
> При проблеме с именем → остановка и запрос (WARNING или BLOCKING).

---

# 6. ПОШАГОВАЯ МОДЕЛЬ РАБОТЫ

## 6.1 Один шаг — одна цель

- Один модуль / функция / действие
- Без «заодно»
- Без забегания вперёд

## 6.2 Обязательная структура шага

Каждый шаг ВСЕГДА:

1. Что делаем и почему
2. Код
3. Тестирование
4. Очистка
5. Стоп

> [!CAUTION]
> Без любого пункта шаг недействителен.

---

# 7. СТАТУС CONFIRMED

## 7.1 Что считается CONFIRMED

Объект считается CONFIRMED, если пользователь:

- Написал «подтверждаю», «ок», «принимаю», «да»
- Дал следующую инструкцию без возражений
- Явно завершил шаг

## 7.2 Последствия

**Для CONFIRMED ЗАПРЕЩЕНО:**
- Любые изменения
- Рефакторинг
- Оптимизация
- Переименование
- Форматирование

Без исключений.

---

# 8. CHANGE REQUEST PROTOCOL

**(Единственный способ менять CONFIRMED)**

## 8.1 Инициация

Change Request допустим ТОЛЬКО, если пользователь:

- Явно указал, что это изменение CONFIRMED
- Чётко обозначил объект и цель

## 8.2 Обязательная структура

1. Что меняется
2. Причина
3. Ожидаемый результат

## 8.3 Поведение агента

- Работать только с указанным объектом
- Один шаг изменения
- Обязательный тест
- Ожидание нового подтверждения

> [!CAUTION]
> Без подтверждения объект НЕ возвращается в CONFIRMED. Любое отклонение → FATAL.

---

# 9. ГРАНИЦЫ ИСПОЛНЕНИЯ

**Агент МОЖЕТ:**
- Работать только с указанными файлами
- Писать код только в разрешённом месте
- Использовать только существующие сущности

**Агент НЕ МОЖЕТ:**
- Редактировать/удалять файлы
- Менять структуру проекта
- Добавлять зависимости
- Менять конфигурации
- Трогать secrets, env, БД-миграции

> [!IMPORTANT]
> Если не разрешено явно — запрещено по умолчанию.

---

# 10. ТЕСТИРОВАНИЕ (ОБЯЗАТЕЛЬНО)

Каждый шаг ОБЯЗАН иметь тест.

**Допустимо:**
- `assert`
- unit-функция
- `input → output`
- Проверка состояния
- Лог + проверяемое условие

**Недопустимо:**
- «Логически верно»
- «Проверим позже»

После теста — обязательная очистка.

# 14. КЛАССИФИКАЦИЯ ОШИБОК

## WARNING
- Риск без нарушения правил
- → Уведомить, можно продолжить

## BLOCKING
- Неоднозначность / конфликт
- → Остановка, запрос инструкции

## FATAL
- Нарушение GEMINI.md или CONFIRMED
- → Полный отказ от выполнения

**Приоритет:**

```
FATAL > BLOCKING > WARNING
```

Формат сообщения об ошибке обязателен.

# 18. ИНФРАСТРУКТУРА И ЗАПУСК ПРОЕКТА

> [!IMPORTANT]
> MiniTMS НЕ запускается локально. Проект работает ТОЛЬКО на удалённом VPS-сервере через Docker Compose.

## 18.1 Сервер

| Параметр | Значение |
|----------|----------|
| IP | `89.167.70.67` |
| Пользователь | `root` |
| Подключение | SSH из PowerShell |

## 18.2 Адреса сервисов

| Сервис | URL |
|--------|-----|
| Frontend (фронт-офис) | `http://89.167.70.67` |
| Backend API | `http://89.167.70.67:8000` |
| API Документация | `http://89.167.70.67:8000/docs` |
| Scraper Browser (noVNC) | `http://89.167.70.67:6080` |

## 18.3 Как запустить / проверить проект

**Шаг 1 — перейти в папку проекта (Windows PowerShell):**
```powershell
cd d:\MiniTMS
```

**Шаг 2 — быстрая проверка состояния сервера (30 сек):**
```powershell
.\check_server.ps1
```

**Шаг 3 — подключение по SSH (если нужны команды на сервере):**
```powershell
.\connect_server.ps1
# или напрямую:
ssh root@89.167.70.67
```

**Шаг 4 — проверить статус контейнеров на сервере (через SSH):**
```bash
docker compose ps
docker compose logs --tail=50 backend
docker compose logs --tail=50 scraping
```

**Шаг 5 — перезапуск сервиса на сервере (через SSH):**
```bash
docker compose restart backend
docker compose restart scraping
```

## 18.4 Стек на сервере

Проект запускается через `docker-compose.yml` (или `docker-compose.remote.yml` для удалённого деплоя). Контейнеры:

| Контейнер | Назначение |
|-----------|------------|
| `minitms-postgres` | База данных PostgreSQL |
| `minitms-redis` | Redis (кэш и очереди) |
| `minitms-backend` | FastAPI бэкенд (порт 8000) |
| `minitms-frontend` | React фронт через Nginx (порт 80) |

## 18.5 Правила для агента

- **НИКОГДА** не пытаться запустить `python`, `uvicorn`, `npm run dev` локально
- **НИКОГДА** не пытаться запустить `docker` локально (Docker не установлен на рабочей машине)
- Для проверки работы — использовать `.\check_server.ps1` или HTTP-запросы к `89.167.70.67`
- Для просмотра логов — подключаться через SSH и запускать `docker compose logs`
- Для проверки скрапера — открыть `http://89.167.70.67:6080` (noVNC браузер скрапера)

## 18.6 Быстрая проверка работы скрапера

1. Открыть в браузере: `http://89.167.70.67` (фронт-офис)
2. Перейти в раздел **«Грузы»**
3. Заполнить форму поиска (место загрузки, место выгрузки)
4. Нажать **«Запустить поиск»**
5. Наблюдать за работой браузера скрапера: `http://89.167.70.67:6080`
6. Дождаться результата (до 3 минут)

> [!NOTE]
> Логи скрапера во время работы: `ssh root@89.167.70.67` → `docker compose logs -f scraping`

> [!IMPORTANT]

- Если хотя бы один пункт — СТОП → остановиться, сообщить причину

**Исключения** (когда открытие НЕ требуется):
- Ответы на информационные вопросы (без изменения кода/файлов)
- Просмотр файлов без изменений
- Проверка статуса/логов

# 21. КОМАНДА /check

Когда пользователь пишет `/check` — агент обязан выполнить следующее:

1. Открыть `d:\MiniTMS\STEP_GATE.md` через `view_file`
2. Явно ответить на каждый из 6 пунктов чеклиста применительно к **последнему выполненному шагу**
3. Перечислить все выявленные нарушения GEMINI.md с указанием номера раздела
4. Предложить конкретный способ устранения каждого нарушения
5. Завершить фразой: **«Шаг завершён. Ожидаю подтверждения или инструкций.»**

Команда `/check` может быть вызвана в любой момент — агент не может отказать в её выполнении.
